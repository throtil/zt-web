# Процедуры

Порядок шагов деплоя, бэкапа, восстановления, откката и замены секретов.
Знание процедуры не должно существовать только в памяти автора: спустя месяцы
без изменений всё восстанавливается отсюда, без реконструкции по истории команд.

Все команды выполняются из каталога рабочей копии на сервере
(в примерах — `/srv/zt-web`), от непривилегированного пользователя,
входящего в группу `docker`.

## Первый подъём на чистом сервере

```bash
# 1. Подготовка хоста (от root): подкачка, sysctl, проверка версий Docker
sudo ./scripts/host-prepare.sh base

# 2. Пользователь и вход по ключу (от root)
sudo ./scripts/host-prepare.sh user zt /tmp/id_ed25519.pub
#    проверить вход по ключу С ДРУГОЙ МАШИНЫ, не закрывая текущую сессию:
#        ssh zt@<адрес> "id && docker ps"
sudo ZT_SSH_HARDEN_CONFIRMED=yes ./scripts/host-prepare.sh ssh-harden

# 3. Каталог под дампы (от root)
sudo ./scripts/host-prepare.sh backup-dir zt /var/backups/zt-web

# 4. Файл окружения
cp .env.example .env
chmod 600 .env
./scripts/gen-secrets.sh          # значения скопировать в .env
$EDITOR .env                      # адрес сайта, учётные записи, доступы к B2

# 5. Стек
docker compose up -d

# 6. Установка WordPress и распределение прав
./scripts/wp-provision.sh
./scripts/check-roles.sh          # проверка прав поведением, а не списком

# 7. Плагины по декларативному списку
./scripts/plugins-sync.sh check

# 8. Расписание бэкапа
sudo install -m 644 deploy/cron/zt-web /etc/cron.d/zt-web   # заменить <логин> и путь
./scripts/backup-db.sh                                      # первый запуск вручную
./scripts/backup-check.sh
```

**После шага 5 — проверить Amnezia.** Отдельной проверкой: подключиться
VPN-клиентом. Из того, что сайт отвечает, работоспособность VPN не следует.

## Деплой

```bash
./scripts/deploy.sh                 # до origin/<текущая ветка>
./scripts/deploy.sh v1.2            # до тега или коммита
```

Скрипт сам: проверяет чистоту рабочей копии, снимает дамп базы, переходит на
целевой коммит, применяет состояние к сервисам, ждёт готовности, приводит набор
плагинов к `plugins.txt` и проверяет, что публичная страница и админка
отвечают. Любой неуспешный шаг останавливает деплой.

Если скрипт сообщил о расхождении рабочей копии с репозиторием — на сервере
что-то правили руками. Это не затирается молча: перенести изменение в
репозиторий либо отменить его (`git restore`, `git clean`) и повторить деплой.

Ожидаемая длительность: 1–3 минуты, из них большая часть — ожидание готовности
сервисов.

### Замечание про редактора

Деплой перезапускает WordPress, и редактор в этот момент может писать статью.
WordPress автосохраняет черновики на сервере, поэтому потеря ограничена
последними правками. Обратной связи между разработчиком и редактором в системе
нет — при заметном неудобстве договариваться по внешнему каналу.

## Откат

```bash
./scripts/rollback.sh               # к предыдущему коммиту из .deploy-history
./scripts/rollback.sh <коммит>      # к указанному
```

Тома состояния не пересоздаются: база, загрузки и `.env` остаются как есть,
поэтому статьи и изображения, добавленные после неудачного деплоя, сохраняются.

Откат возвращает **код**, но не состояние базы. Если неудачный деплой изменил
схему базы (обновление ядра или плагина), к прежнему поведению возвращает
восстановление дампа, который деплой снял перед применением.

После откката рабочая копия в отсоединённом состоянии. Вернуться к ветке:
`git checkout master`.

Ожидаемая длительность: 1–3 минуты.

## Бэкап базы

Запускается по расписанию из `/etc/cron.d/zt-web`; вручную:

```bash
./scripts/backup-db.sh              # дамп, проверка, выгрузка в B2, очистка старых
./scripts/backup-db.sh --local      # только локально, без B2
./scripts/backup-check.sh           # свежесть последней годной копии
```

Порядок в скрипте не произвольный: свободное место проверяется до дампа, дамп
проверяется на непустоту и целостность до любого удаления, старые копии
удаляются только после того, как новая признана годной и оказалась в B2.
Неудачный дамп годные копии не вытесняет.

Медиа не резервируется — это известное ограничение итерации, см.
[limitations.md](limitations.md).

## Восстановление базы

Ожидаемая длительность на базе первых десятков статей — **до 5 минут**,
из них сам импорт занимает секунды; остальное — проверка дампа, остановка и
запуск WordPress, проверка ответа сайта. Скрипт печатает фактическую
длительность: сверять с этой оценкой.

```bash
./scripts/restore-db.sh --latest --yes                  # из последней локальной копии
./scripts/restore-db.sh --from-b2 <имя файла> --yes     # из копии в B2
./scripts/restore-db.sh /путь/к/дампу.sql.gz --yes      # из конкретного файла
```

Дамп проверяется до того, как что-то тронуто: непригодный файл не доводит до
затирания базы. Тома при восстановлении не пересоздаются.

### Учебное восстановление на отдельной копии

Выполняется до аварии, а не после. Рабочий сайт при этом не затрагивается:
используется отдельный проект Compose со своими томами.

```bash
# 1. Отдельная копия стека рядом, со своим именем проекта и своими томами
cp -r /srv/zt-web /tmp/zt-restore-drill && cd /tmp/zt-restore-drill
sed -i 's/^name: zt-web$/name: zt-restore-drill/' docker-compose.yml
# в .env: ZT_SITE_ADDRESS=:8081, ZT_SITE_URL=http://<адрес сервера>:8081
docker compose up -d

# 2. Восстановление на копии
./scripts/restore-db.sh --latest --yes

# 3. Проверить, что сайт на копии открывается и статьи на месте, затем убрать
docker compose down --volumes && cd / && rm -rf /tmp/zt-restore-drill
```

Порт 8081 на время учения публикуется дополнительно. Файрвол при этом не
настраивается (см. `design.md`), поэтому копию нужно убрать сразу после
проверки, а не оставлять работающей.

## Проверка разделения прав

```bash
./scripts/check-roles.sh            # проверить
./scripts/check-roles.sh --keep     # оставить временную учётную запись для разбора
```

Скрипт проверяет не список прав, а поведение: заводит временную учётную запись
с ролью `editor`, входит ею в админку по HTTP и убеждается, что полный цикл
заполнения обзора проходит (черновик, публикация, правка после публикации,
загрузка в медиабиблиотеку, категория и метка), а установка плагинов,
обновление ядра, управление пользователями и настройки сайта — нет. Отдельно
проверяет, что редактор файлов темы закрыт и администратору.

Ничьих паролей не требует и в конце удаляет всё, что создал. Запускать после
`wp-provision.sh`, после пересоздания сервера и при любом сомнении в правах —
в том числе когда редактор сообщает о нехватке прав: ответ на вопрос
«действительно ли не хватает» должен давать скрипт, а не выдача роли
администратора.

## Замена пароля базы данных

Замена скомпрометированного секрета не требует пересоздания сервера.

```bash
# 1. Новое значение
./scripts/gen-secrets.sh db

# 2. Сменить пароль пользователя в самой базе (старое значение ещё в .env)
docker compose exec -T -e MYSQL_PWD="<старый root-пароль>" db \
  mariadb --user=root -e \
  "ALTER USER '<ZT_DB_USER>'@'%' IDENTIFIED BY '<новый пароль>'; FLUSH PRIVILEGES;"

# 3. Записать новое значение в .env (ZT_DB_PASSWORD), затем
docker compose up -d wordpress

# 4. Проверить: сайт открывается, админка работает
./scripts/backup-check.sh   # заодно убедиться, что дампы всё ещё создаются
```

Проверка, что старое значение больше не действует:

```bash
docker compose exec -T -e MYSQL_PWD="<старый пароль>" db \
  mariadb --user=<ZT_DB_USER> -e "SELECT 1;"   # должно завершиться ошибкой доступа
```

### Пароль root

Меняется так же, но root-записей в базе может быть две — `root@localhost` и
`root@'%'`, — и замена одной оставляет вторую со старым паролем. Проверить,
что есть, и заменить всё разом:

```bash
# 1. Какие записи root существуют
docker compose exec -T -e MYSQL_PWD="<старый root-пароль>" db \
  mariadb --user=root -e "SELECT user, host FROM mysql.user WHERE user='root';"

# 2. Заменить пароль у каждой из показанных записей
docker compose exec -T -e MYSQL_PWD="<старый root-пароль>" db \
  mariadb --user=root -e "
    ALTER USER 'root'@'localhost' IDENTIFIED BY '<новый пароль>';
    ALTER USER 'root'@'%'         IDENTIFIED BY '<новый пароль>';
    FLUSH PRIVILEGES;"

# 3. Записать новое значение в .env (ZT_DB_ROOT_PASSWORD), затем проверить
#    именно тот путь, которым ходит cron: снятие дампа
./scripts/backup-db.sh --local
```

Дамп снимается от root, поэтому неполная замена ломает бэкап — и обнаружится
это не сразу, а первым ночным запуском.

Запись `root@'%'` даёт доступ от root по сети из любого контейнера сети `data`,
включая контейнер сайта, и никому не нужна: и дамп, и восстановление ходят
через сокет внутри контейнера базы. На новых установках её не появляется —
`MARIADB_ROOT_HOST: localhost` в описании стека. На базе, созданной до этого,
убрать вручную, проверив перед этим, что дамп снимается:

```bash
docker compose exec -T -e MYSQL_PWD="<root-пароль>" db \
  mariadb --user=root -e "DROP USER 'root'@'%';"
```

## Замена солей и ключей WordPress

```bash
./scripts/gen-secrets.sh salts     # восемь новых значений в .env
docker compose up -d wordpress
```

Сайт продолжает работать, но все ранее выданные сессии становятся
недействительными: и разработчику, и редактору потребуется войти заново.
Это ожидаемое поведение, а не признак поломки, — предупредить редактора заранее.

Пересборка образа не нужна: значения приходят из окружения при запуске.

## Правки в дополнениях к wp-config.php

Файл `config/wordpress/wp-config-zt.php` подключается через `require`, поэтому
его правки применяются перезапуском стека:

```bash
docker compose up -d wordpress
```

Пересоздавать `wp-config.php` не требуется. Это как раз причина, по которой
дополнения лежат в отдельном файле, а не в `WORDPRESS_CONFIG_EXTRA`: содержимое
переменной попадает в `wp-config.php` один раз, при первом старте.

## Локальная копия для разработки

```bash
cp .env.example .env         # локально достаточно заглушек
./scripts/gen-secrets.sh     # значения в .env
./scripts/local-up.sh        # http://localhost:8080
ZT_LOCAL=1 ./scripts/wp-provision.sh
./scripts/local-up.sh down   # остановить
./scripts/local-up.sh reset  # удалить локальные тома и поднять заново
```

Локальная копия использует свои тома: её данные и данные сервера не
пересекаются. Caddy и TLS локально не участвуют.
