## Purpose

Описывает, как трафик посетителя попадает в WordPress: точка терминации HTTPS, выпуск и продление сертификата, и корректная работа приложения за обратным прокси. Без этого WordPress генерирует ссылки по неверной схеме и видит вместо посетителей IP прокси.

## ADDED Requirements

### Requirement: Весь публичный трафик идёт по HTTPS

Система SHALL принимать запросы на портах 80 и 443. Запрос по HTTP MUST получать постоянный редирект на тот же адрес по HTTPS.

#### Scenario: Обращение по HTTP
- **WHEN** посетитель открывает адрес сайта по схеме `http://`
- **THEN** он получает постоянный редирект на тот же путь по схеме `https://`

#### Scenario: Обращение по HTTPS
- **WHEN** посетитель открывает адрес сайта по схеме `https://`
- **THEN** соединение устанавливается с действительным сертификатом для этого домена, без предупреждений браузера

### Requirement: Сертификат выпускается и продлевается автоматически

Система SHALL получать TLS-сертификат для домена без участия человека и продлевать его до истечения срока. Ручные шаги MUST NOT требоваться ни при первом выпуске, ни при продлении.

#### Scenario: Первый выпуск после появления DNS
- **WHEN** DNS-запись домена указывает на сервер и стек запускается
- **THEN** сертификат для домена выпускается автоматически, и сайт становится доступен по HTTPS

#### Scenario: Приближение срока истечения
- **WHEN** до истечения срока действия сертификата остаётся меньше порога продления
- **THEN** сертификат продлевается автоматически, и посетители не видят перерыва в обслуживании

#### Scenario: Сертификат переживает перезапуск
- **WHEN** стек остановлен и запущен заново
- **THEN** ранее выпущенный сертификат используется повторно, без нового обращения к центру сертификации

### Requirement: WordPress корректно работает за обратным прокси

Приложение SHALL распознавать, что исходный запрос пришёл по HTTPS, и SHALL видеть настоящий IP-адрес посетителя. Генерируемые приложением абсолютные ссылки, редиректы и ресурсы страницы MUST использовать схему `https` и канонический домен.

#### Scenario: Ссылки и ресурсы на странице
- **WHEN** посетитель открывает любую страницу сайта по HTTPS
- **THEN** все ссылки и подключаемые ресурсы, сгенерированные приложением, используют схему `https`, и браузер не сообщает о смешанном содержимом

#### Scenario: Вход в админку не уходит в цикл редиректов
- **WHEN** посетитель открывает страницу входа в админку по HTTPS и выполняет вход
- **THEN** вход завершается успешно, без бесконечного цикла редиректов

#### Scenario: Настоящий IP посетителя
- **WHEN** запрос посетителя проходит через обратный прокси
- **THEN** приложение и его журналы фиксируют IP-адрес посетителя, а не адрес прокси

### Requirement: Один канонический домен

Система SHALL обслуживать сайт по одному каноническому имени. Обращения по прочим именам, указывающим на этот сервер, MUST получать постоянный редирект на каноническое имя.

#### Scenario: Обращение по неканоническому имени
- **WHEN** посетитель открывает сайт по альтернативному имени, указывающему на тот же сервер
- **THEN** он получает постоянный редирект на каноническое имя

### Requirement: Загрузка крупных файлов не обрывается

Тракт приёма запросов SHALL допускать загрузку файлов размером до предела, заданного конфигурацией, и этот предел MUST быть согласован между обратным прокси и приложением. Загрузка файла в пределах лимита MUST NOT обрываться по превышению размера или по таймауту.

#### Scenario: Загрузка фотографии максимального размера
- **WHEN** редактор загружает через админку изображение размером, равным заданному пределу
- **THEN** загрузка завершается успешно, без ошибки превышения размера и без обрыва по таймауту

#### Scenario: Превышение предела
- **WHEN** редактор загружает файл больше заданного предела
- **THEN** он получает понятное сообщение об ошибке, а не пустую страницу или обрыв соединения

### Requirement: Работа через сторонний CDN не ломает сайт

Система SHALL корректно обслуживать трафик как при прямом обращении к серверу, так и когда перед ним стоит внешний CDN, терминирующий TLS. Требования о схеме ссылок и настоящем IP посетителя MUST выполняться в обоих режимах.

#### Scenario: Включён проксирующий режим CDN
- **WHEN** DNS-запись домена переключена в проксирующий режим внешнего CDN
- **THEN** сайт остаётся доступен по HTTPS, ссылки используют схему `https`, цикл редиректов не возникает, и приложение видит IP посетителя, а не узла CDN

#### Scenario: Обход CDN для проверки
- **WHEN** запрос отправлен напрямую на адрес сервера, минуя CDN, с указанием канонического имени
- **THEN** сервер отвечает по HTTPS с действительным сертификатом
