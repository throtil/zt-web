## Purpose

Описывает, какие секреты нужны сайту, как они попадают в контейнеры и почему они не могут оказаться в git. Установлено первым, потому что медиа-пайплайн добавит ключи объектного хранилища, а менять способ доставки секретов потом дороже, чем задать его сразу.

## ADDED Requirements

### Requirement: Секреты не попадают в репозиторий

Ни один действующий секрет SHALL NOT находиться в версионируемых файлах. Репозиторий MUST содержать только образец файла окружения с именами переменных, их назначением и заведомо нерабочими значениями-заглушками.

#### Scenario: Проверка перед коммитом
- **WHEN** файл окружения с действующими секретами создан на сервере рядом с рабочей копией
- **THEN** он не попадает в индекс и не показывается как неотслеживаемое изменение

#### Scenario: Новый участник или новая машина
- **WHEN** репозиторий склонирован на чистую машину
- **THEN** в нём есть образец файла окружения, по которому видно полный перечень требуемых переменных, и нет ни одного действующего значения

### Requirement: Полный перечень секретов задан явно

Система SHALL иметь единый список требуемых секретов: учётные данные базы данных, соли и ключи аутентификации WordPress, а также, по мере появления, доступы к объектному хранилищу и внешним сервисам. Каждая запись MUST указывать назначение переменной и то, где взять её значение.

#### Scenario: Сверка окружения с образцом
- **WHEN** файл окружения на сервере сверяется с образцом из репозитория
- **THEN** расхождение в наборе переменных обнаруживается явно, до запуска стека

### Requirement: Отсутствующий секрет останавливает запуск

Запуск стека SHALL прерываться с понятным сообщением, если обязательная переменная окружения не задана или пуста. Система MUST NOT подставлять значение по умолчанию для пароля базы данных или для солей WordPress.

#### Scenario: Пропущена переменная
- **WHEN** предпринимается запуск стека с файлом окружения, в котором отсутствует обязательная переменная
- **THEN** запуск завершается ошибкой с указанием имени недостающей переменной, и сайт не поднимается в небезопасной конфигурации

#### Scenario: Пустое значение вместо пропуска
- **WHEN** обязательная переменная присутствует, но её значение пусто
- **THEN** поведение то же, что при её отсутствии: запуск прерывается с указанием имени переменной

### Requirement: Секреты доставляются в контейнеры через окружение, а не через образ

Значения секретов SHALL передаваться сервисам во время запуска. Они MUST NOT записываться в образы контейнеров и MUST NOT попадать в версионируемые файлы конфигурации приложения.

#### Scenario: Осмотр образа
- **WHEN** собранный образ контейнера осматривается на предмет содержимого и истории слоёв
- **THEN** действующих секретов в нём нет

#### Scenario: Смена значения секрета
- **WHEN** значение секрета изменено в файле окружения и стек перезапущен
- **THEN** сервисы начинают использовать новое значение без пересборки образа

### Requirement: Файл секретов защищён на уровне прав доступа

Файл окружения на сервере SHALL быть читаем только владельцем. Права, дающие чтение прочим пользователям хоста, MUST рассматриваться как дефект конфигурации.

#### Scenario: Проверка прав
- **WHEN** проверяются права доступа к файлу окружения на сервере
- **THEN** чтение и запись разрешены только владельцу, остальным доступ закрыт

### Requirement: Секрет можно заменить по известной процедуре

Для каждого секрета SHALL быть описан порядок замены: что поменять, что перезапустить и как убедиться, что сайт работает. Замена скомпрометированного секрета MUST NOT требовать пересоздания сервера.

#### Scenario: Замена пароля базы данных
- **WHEN** пароль базы данных заменяется по описанной процедуре
- **THEN** после её выполнения сайт открывается и обращается к базе с новым паролем, а старое значение больше не действует

#### Scenario: Замена солей WordPress
- **WHEN** соли и ключи аутентификации WordPress заменяются по описанной процедуре
- **THEN** сайт продолжает работать, а ранее выданные сессии становятся недействительными и требуют повторного входа
